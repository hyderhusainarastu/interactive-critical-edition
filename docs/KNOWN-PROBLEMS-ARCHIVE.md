## Known Problems — settled / one-time (moved 2026-07-23)

- **`supabase storage cp` cannot copy directly between two buckets** (discovered 2026-07-20, Phase 10 canary) — `supabase storage cp ss:///bucket-a/x ss:///bucket-b/y --linked --experimental` fails with `LegacyStorageCopyBetweenBucketsError: Copying between buckets is not supported`, even though same-bucket copies and local↔remote transfers both work fine. Workaround: two single-bucket operations — `supabase storage cp ss:///bucket-a/x <local-tmp-path> --linked --experimental` (download) then `supabase storage cp <local-tmp-path> ss:///bucket-b/y --linked --experimental` (upload) — round-tripping through a local temp file. This is how the private `eval-fixtures` → `documents` fixture copy was done for this canary, instead of the single-command copy prior canary narratives implied.
- **`docker compose` plugin isn't found by default after `brew install docker-compose`:** Homebrew's Docker CLI doesn't look in `/opt/homebrew/lib/docker/cli-plugins` unless told to. Fix (already applied, `~/.docker/config.json`): add `"cliPluginsExtraDirs": ["/opt/homebrew/lib/docker/cli-plugins"]`.
- **Render needs a GitHub connection made through its dashboard before it can fetch even a repo the user already owns** — `render services create --repo ...` fails with "invalid or unfetchable" until GitHub is explicitly connected under Render's Account Settings → Connected Accounts (an OAuth step, done by the user; no CLI equivalent found). This is a different model from Vercel, whose CLI uploads local files directly and doesn't need this step to deploy via CLI.
- **Render requires a payment method before creating *any* paid-plan service, not just at billing time** — `render services create --plan starter` fails with HTTP 402 ("Payment information is required") until a card is added under Render's dashboard billing page, even though the free tier exists for other service types. Confirms the plan's own prediction that Render's worker is the one cost in this stack that isn't $0.
- **Vercel + pnpm monorepo: deploying from the app subdirectory silently breaks the build.** Running `vercel link`/`vercel --prod` from inside `apps/web` uploads only that subtree, so Vercel never sees the root `pnpm-lock.yaml`/`pnpm-workspace.yaml` and falls back to `npm install` (which then fails on the workspace-only `@ice/db` dependency). Fix: set the Vercel project's **Root Directory** to `apps/web` (no CLI flag for this — used `vercel project update` first, which lacks a root-directory option, then the REST API: `PATCH /v9/projects/:id?teamId=...` with `{"rootDirectory":"apps/web"}`), then deploy **from the repo root** so the whole monorepo — including the root lockfile — gets uploaded and Vercel `cd`s into Root Directory to build.
- **Vercel REST API calls need the *actual* `orgId`, not a value hand-transcribed from a JWT.** A `PATCH` to `/v9/projects/:id?teamId=...` returned "Not authorized" using a `teamId` misread from the `VERCEL_OIDC_TOKEN` payload (visually similar-looking ID, one character off). The authoritative value is in `.vercel/project.json` (`orgId`) written locally by `vercel link` — use that, not a manually parsed token.
- **Route protection resolved in Phase 2** (superseding the Phase 1 note that used to be here): centralized via `requireSession()` (pages — redirects to `/login`) and `getApiUserId()` (API routes — returns `null` for the caller to turn into a 401) in `apps/web/src/lib/auth.ts`, used by the `(app)` layout and every protected route instead of ad hoc `auth()` calls. Still Node-runtime, not Edge middleware, for the same `sessionVersion`/`postgres.js` reason as before.
- Trivial, non-blocking CI annotation: `pnpm/action-setup@v4` is flagged by GitHub as targeting a deprecated Node 20 runner internally (it still runs fine, forced onto Node 24). Bump to a newer major when one addresses this.
- **Historical iCloud failure (fixed by moving the repo).** Until 2026-07-20 this repo lived under `~/Documents`; iCloud could evict a `node_modules` file as `dataless` and a read could return an empty module, causing nonsense such as `Right-hand side of 'instanceof' is not an object` or a non-zero migration with no message. It now lives at `/Users/hyderhusainarastu/Project/AutoCriticalEditionProject`, outside iCloud Drive, and `pnpm install` was re-run successfully after the move. If an old checkout is used, diagnose with `ls -lO <file>` and recover with `brctl download <file>`.
- **Vercel stores `DATABASE_URL`/`DIRECT_URL` as *Sensitive* env vars, so `vercel env pull` returns a ~13-char placeholder, not the real connection string** (discovered Phase 4). Sensitive vars are write-only — they decrypt only at build time, never back through the CLI/API. Consequence: the documented `vercel env pull` → run-migration path does **not** work for these. Phase 4's production migration was instead applied via the **Supabase Management API** SQL endpoint (`POST https://api.supabase.com/v1/projects/:ref/database/query`, Bearer = the Supabase access token — no DB password needed). When doing that, also insert the drizzle bookkeeping row so future `drizzle-kit migrate` stays consistent: `INSERT INTO drizzle.__drizzle_migrations (hash, created_at) VALUES ('<sha256 of the raw .sql file>', <the entry's "when" from meta/_journal.json>)` — drizzle gates by the `created_at` timestamp, so this is what marks the migration applied.
- **The Supabase Management API is behind Cloudflare, which blocks default library User-Agents** (Python `urllib` → HTTP 403 "error code: 1010"). Use `curl` (its UA passes) with `--data-binary @file.json` to avoid both the UA block and shell-quoting hell on the SQL payload. Build the JSON body with a Python heredoc writing to a file, then `curl` that file.
- **Invalid-password login — FIXED (Phase 8.1).** Root cause: Auth.js v5 `signIn` **throws** a `CredentialsSignin`/`AuthError` when `authorize()` rejects (it does not return `{ error }`), so `loginAction`'s old `if (result?.error)` branch was never reached and the throw surfaced as an unhandled runtime error. Fix: `loginAction` now wraps `signIn` in try/catch, redirects `AuthError` → `/login?error=1` (the login page already renders the friendly message), and re-throws everything else — crucially the `NEXT_REDIRECT` thrown by `redirect()`, which must propagate. Kept as a note so the pattern isn't reintroduced.

## Important Design Decisions — narrow UI-detail rows (moved 2026-07-23)

Verbatim rows from the project log's decision table, in their original order. Format: `| Decision | Rationale |`.

| Decision | Rationale |
|---|---|
| Credibility gets a discrete 3-band meter (`CredibilityMeter.tsx`), not a continuous-gradient bar, and it's shown *alongside* the existing letter-grade `AuthorityBadge`, not replacing it | A continuous fill from `credibility.score` would imply a precision the underlying heuristic-derived score doesn't have (plan §36 11.2); three bands (critical/mixed/good) say only as much as the data supports. Kept beside `AuthorityBadge` rather than swapped in because the two answer different questions — authority (A–E, source-type rigor) vs. an aggregate score — and this project's stance has consistently been to add independent signals rather than collapse them (same reasoning as 9.2a keeping credibility dimensions separated and popularity display-only) |
| `--color-credibility-critical`/`--color-credibility-warning` are new, more-saturated functional accent tokens scoped only to credibility alerting, not a general brightness increase across the palette | The user's "harsher/brighter" feedback (plan §36 context) was specifically about missing a low-credibility source at a glance, not about the palette's overall calm/warm register — so the more saturated red/amber pair is reserved for that one purpose, "good" reuses the existing `--color-accent-green` rather than inventing a second green, and the general-UI contrast ask (thicker `:focus-visible` outline, darker light-theme `--color-text-muted`/`--color-border`, lighter dark-theme equivalents) was handled as a token-value tune-up on the existing palette instead |
| Annotation marker colors set via one inline `--reader-annotation-color` custom property (from `CATEGORY_META.colorVar`) rather than a parallel `.reader-annotation-{category}` CSS class list | `annotationMeta.ts`'s `CATEGORY_META` already carried the correct color-per-category mapping; `globals.css` had a second, hand-kept mapping that had to be updated in lockstep with the first or the two would drift. Collapsing to one source of truth (`highlightDom.ts` sets the CSS var directly on each marker element) means a category's color can never disagree between the component data and the stylesheet again |
| The upload-progress step list required no new polling logic | Investigating it surfaced that `handleEditionExtraction` (the real `extract-text` job handler for v2/v3) runs the *entire* edition pipeline — extraction through classification — inside that one job, with `document.processingStatus` staying `"processing"` the whole time; `WorkStatusPanel`'s pre-existing polling (`POLLING_STATUSES` includes `"processing"`) already covers this window. The gap was only ever a rendering one (a bare stage string, not a step list), not a missing-polling one — worth recording since it revises what earlier phases' documentation implied about when "processing" ends |
| Passage-annotation sidebar cards derive their expanded state (`open \|\| active`) rather than `setState`-ing it inside a `useEffect` on becoming active | The obvious implementation — an effect that calls `setOpen(true)` when a card becomes `active` — trips this codebase's own lint rule against synchronous `setState` inside an effect body (cascading-render risk). A derived boolean achieves the same "click-to-reveal auto-expands" UX with no effect at all; the sidebar's tab-switch-on-marker-click is the one place in this sub-phase that genuinely needs an effect-driven external-prop sync (switching tabs is not itself derivable from `activeId` alone, since the reader must still be free to navigate back to Sources afterward), handled with the same `eslint-disable-next-line` precedent `LibraryView.tsx` already established for an analogous one-shot sync |
