## Notes on severity classification

D-19-1 is P1 rather than P2 because it is simultaneously (a) a CI-blocking regression on `main` and (b) a genuine WCAG accessible-name-uniqueness problem in a shipped, authenticated surface — not merely cosmetic. D-19-2 is P2, not P1: no data is lost, no core workflow breaks, and the underlying documents really are gone (correct outcome), but the operational-noise/false-alarm risk is real enough not to be P3. D-19-3 is P1: a full, multi-hour production worker outage is exactly the plan's P1 definition ("processing failure ... inaccessible primary workflow"), even though the code fix itself predates this register entry — the entry exists to close the documentation gap and record the incident where the plan requires it to live. D-19-4 is P1: it broke CI on `main` (same bar as D-19-1) — recorded honestly as a defect this same session introduced and caught, not omitted because it was self-inflicted. D-19-5 is P2, not P1: the real, production upload → confirm → analyze journey is not shown to be broken (the confirm-metadata step's own component was read and confirmed unchanged) — only the *tests'* navigation assumption had gone stale — but it's exactly the kind of drift that leaves a core journey effectively unverified for multiple phases, which is a real audit-scope finding even though nothing shipped broken to users. D-19-6 is P2: nothing here shows production is broken either (every sub-finding is either a deliberate, already-shipped Phase 11.5 design decision, or a local-only environment misconfiguration that made tests silently exercise the wrong pipeline) — but a multi-phase environment drift that left the project's own full-stack verification testing a retired code path is exactly the kind of finding this audit exists to surface, and the legacy-panel reachability question is real enough to need an owner decision, not a silent close. D-19-7 is P1, not P2, on the strength of the `hardening.spec.ts` sub-finding specifically: a green accessibility/hardening test that was actually scanning the wrong page is a false-confidence result on a real WCAG-scoped surface — closer in kind to D-19-1's "the check itself was broken" than to D-19-6's honest environment gap, even though (like D-19-6) production itself is not shown to be affected. D-19-8 is P3: the net result is new test coverage plus one small stale-text fix, and zero real accessibility violations were found across 11 previously-unscanned routes — a good outcome, recorded for its own sake and because ruling out two plausible false-positive explanations along the way is itself useful evidence for future accessibility-test authors on this codebase. D-19-9 is P2: it blocks a clean local E2E run but not users or CI. D-19-10 is P1 because it enables a persistent authenticated quota bypass and lets unverified bytes enter the processing path. D-19-11 is P2: it is bounded, measured production lifecycle debt with no current broken references, but it persists private source data beyond its owner and needs an authorized cleanup rather than a paper close. D-19-12 is P3: it is a real, reproducible CI-test flake caused by hidden Next streaming markup, but it does not expose a duplicate control to users or assistive technology. D-19-13 through D-19-15 are P2 because each is a real keyboard/modal-accessibility failure on an authenticated authoring or navigation surface: the underlying work remains possible with a pointer, but the focused control itself is misleading or fails expected modal behavior for keyboard and assistive-technology users. D-19-16 is P2 because it hides the selected state of a primary Library filter from assistive technology while leaving the underlying list operation available; it is more than cosmetic but does not block access to the shelf. D-19-17 is P2 because an ambiguous accessible name routes keyboard/assistive-technology users between a global and a work-specific research surface; it affects a primary work-navigation action but has an unambiguous visual distinction for pointer users.
