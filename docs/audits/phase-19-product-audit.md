## Notes on severity classification

D-19-1 is P1 rather than P2 because it is simultaneously (a) a CI-blocking regression on `main` and (b) a genuine WCAG accessible-name-uniqueness problem in a shipped, authenticated surface — not merely cosmetic. D-19-2 is P2, not P1: no data is lost, no core workflow breaks, and the underlying documents really are gone (correct outcome), but the operational-noise/false-alarm risk is real enough not to be P3. D-19-3 is P1: a full, multi-hour production worker outage is exactly the plan's P1 definition ("processing failure ... inaccessible primary workflow"), even though the code fix itself predates this register entry — the entry exists to close the documentation gap and record the incident where the plan requires it to live. D-19-4 is P1: it broke CI on `main` (same bar as D-19-1) — recorded honestly as a defect this same session introduced and caught, not omitted because it was self-inflicted. D-19-5 is P2, not P1: the real, production upload → confirm → analyze journey is not shown to be broken (the confirm-metadata step's own component was read and confirmed unchanged) — only the *tests'* navigation assumption had gone stale — but it's exactly the kind of drift that leaves a core journey effectively unverified for multiple phases, which is a real audit-scope finding even though nothing shipped broken to users. D-19-6 is P2: nothing here shows production is broken either (every sub-finding is either a deliberate, already-shipped Phase 11.5 design decision, or a local-only environment misconfiguration that made tests silently exercise the wrong pipeline) — but a multi-phase environment drift that left the project's own full-stack verification testing a retired code path is exactly the kind of finding this audit exists to surface, and the legacy-panel reachability question is real enough to need an owner decision, not a silent close.
