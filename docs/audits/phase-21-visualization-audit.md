## 1. Phase 21.1 — Graph data contract

**Core question: is the payload one shared dataset, or independently filtered per view?**

**Finding: one shared dataset — already correct.** Trace:

1. `GraphView.tsx:74-88` fetches the endpoint exactly once into `data` state.
2. `GraphView.tsx:146` — `const filtered = useMemo(() => (data ? filterGraphData(data, filters, pinnedWorkIds) : null), [data, filters, pinnedWorkIds]);` — **one** call to `filterGraphData`.
3. `GraphView.tsx:401` passes `filtered` into `<KnowledgeGraph3D data={filtered} ... />`.
4. `GraphView.tsx:409` passes the **same** `filtered` into `<GraphAccessibleFallback data={filtered} ... />`.

Both views consume the identical filtered node/link arrays from one filter pass. `types.ts:185-221`'s own doc comment states this is deliberate ("Never derive different filtered datasets separately for the scene and table" — 21.1's own words, verbatim, already in the code comment). **No defect here; this satisfies 21.1's central requirement already.** Sorting inside the table (`GraphAccessibleFallback.tsx:43-51`) is local display-only and does not diverge the underlying set.

**Field-by-field check of the required node/edge contract (21.1):**

`GraphNode` (`types.ts:4-32`) has: `id` ✅, `type` ✅ (entity type), `label` ✅, no dedicated **secondary label** field (authors/year are separate optional fields, used ad hoc per view — not a single "secondary label" slot), `state` ✅ (maps to reading status), `credibilityScore` ✅, `provenance`/`provenances` ✅. Two required fields are **not present as node-level data at all**:

- **"uploaded/private status"** — approximated by `type === "work"` / `state === "primary"`, but there is no explicit boolean distinguishing "this is the reader's own private upload" from "this is a public/shared entity," which is exactly the ambiguity 21.8 also flags (see §21.8 below, "Your work" → "Uploaded work" label fix already landed mid-audit by a concurrent agent, `git diff apps/web/src/components/graph/types.ts`).
- **"associated work IDs"** — not stored on the node at all. `GraphFilters.associatedWork` (`types.ts:187-199`) computes a node's work association **at filter time** by walking `data.links` for every filter invocation, rather than the node carrying a precomputed `workIds: string[]`. Functionally equivalent for filtering, but means no other consumer (inspector, table column, future feature) can read "which works is this node associated with" without re-deriving it from edges.
- **"navigable destination when available"** — absent entirely. No node carries a `href`/`destination` field. The inspector (`GraphView.tsx:472`) only renders `selected.url` (an **external** URL) or nothing. There is no internal navigation from a graph node to, e.g., the new `/library/[resourceId]` page (see §6) or `/works/[workId]`. `GraphAccessibleFallback.tsx:139` similarly only ever links `node.url` (external), never an internal route.

`GraphLink` (`types.ts:34-45`) has: `source`/`target` ✅, `edgeType` ✅ (relation type), `category` ✅ (partially — see next), `confidence` ✅, `evidence`/`provenance` ✅. Two gaps:

- **"human-readable relation label"** exists only as a derived function (`edgeTypeLabel()`, `types.ts:93-95`, a bare `replace(/_/g, " ")`) — not a stored/curated label. This is the same underlying gap flagged in 21.8 (no reuse of `CATEGORY_META`'s curated labels for edges).
- **"direction"** is implicit only in which end is `source` vs `target`; there is no explicit `directed: boolean` or direction-adjective field for edges that are inherently bidirectional (`is_comparable_to`) vs. strictly directed (`cites`). The 3D scene always renders directional particles (`KnowledgeGraph3D.tsx:260-266`) regardless of whether the underlying relation is actually directional.
- **`category`, in practice, is frequently `null`.** `graph.ts:184` and `graph.ts:242` read `(evidence->>'category') AS category` from the `graph_edge.evidence` jsonb column, but only the classification-derived edges populate `evidence.category` (`apps/worker/src/analyze.ts:722`, `:1662`). The citation "cites" edge's evidence shape (`analyze.ts:560-566`, `{ citationId, sourceType, anchor }`) and the concept "presupposes" edge's evidence shape (`analyze.ts:~1275`, `{ role, reason }`) **never set `category`** — so `link.category` is `null` for citation edges and concept edges, and is also never populated for the source-discovery/source-relation edges built directly in `graph.ts:476-498` (no `category` key set there either, aside from the hardcoded `"source_provenance"` literal at `graph.ts:494`). This matters directly for 21.8's requirement to show "relationship-category label... where the landing depiction uses it": most edges in the graph simply have no relationship-category value to show.

**Verdict:** 21.1's headline risk (independently-filtered datasets) is already resolved. The remaining gaps are contract *completeness* gaps (missing `destination`, missing stored `associatedWorkIds`, inconsistent `category` population, no explicit `directed` flag) — real, but narrower than the plan's framing implies.

**Edge integrity gap found while tracing writes (new finding, not previously documented anywhere):**

- `analyze.ts:1269` (concept `presupposes` edge) — **guarded** by an `existingEdge` SELECT at `1255-1268` before insert.
- `analyze.ts:1664` (work → bibliographic_record classification edge, e.g. `disagrees_with`/`is_prerequisite_for`/etc.) — **not guarded** by any existence check.

Unlike `analyzeWork()` (the legacy v1 path, `analyze.ts:574`), which explicitly clears all prior system-created `graph_edge` rows for the work before re-classifying (`analyze.ts:601-611`: `.delete(annotations)...`, `.delete(citations)...`, `.delete(graphEdges).where(and(sourceType='work', sourceId=doc.workId, createdBy='system'))`), **`analyzeEditionRun()` has no equivalent clearing step anywhere in its body** (`grep -n "delete(graphEdges" apps/worker/src/analyze.ts` returns exactly one hit, inside `analyzeWork`, not `analyzeEditionRun`). `graph_edge` also carries no `run_id` column at all (`schema.ts:591-612`), so nothing scopes these rows to a processing run the way `research_resource`/`passage_annotation`/`edition_relation` are scoped and superseded via `processing_run.is_published`.

**Consequence:** reprocessing an edition-pipeline work whose reclassification changes category between runs (exactly the kind of change the Phase 11.7 relevance fix made in production, per PROJECT-LOG) leaves the **old** edge (old `edgeType`) in the table alongside the **new** one, because `graph.ts`'s read-time dedup (`linkByIdentity`, `types.ts` equivalent logic in `graph.ts:543-567`) only collapses edges with an *identical* `(source, target, edgeType)` triple — a changed `edgeType` is a different key, so both survive and both render as if the work has two simultaneous, contradictory relationships to the same reference. Re-running the same classification twice with the *same* category is invisible (the read-side dedup absorbs it), so this defect is real but only surfaces on a reprocess that changes the classification outcome — plausible, not yet reproduced live (see contention note in the header).

## 3. Phase 21.3 — Repair relation filters

**Trace: control → URL → filter object → filtering function → rendered nodes/edges → table.**

1. Control: `<select value={filters.relation} onChange={(e) => updateFilter("relation", e.target.value)}>` — `GraphView.tsx:270-286`.
2. `updateFilter` (`GraphView.tsx:90-103`) updates React state **and** the URL via `router.replace`, keyed on `FILTER_KEYS` (`GraphView.tsx:33`).
3. On mount/reload, `filtersFromParams(searchParams)` (`GraphView.tsx:36-43`) rehydrates `filters` state from the URL — confirmed round-trip.
4. `filtered = filterGraphData(data, filters, pinnedWorkIds)` (`GraphView.tsx:146`) is the single filtering call feeding both views (§21.1).
5. Inside `filterGraphData` (`types.ts:185-221`):
   - Nodes are filtered by `byNode.get(n.id)?.has(filters.relation)` (`types.ts:214`) — i.e., **"does this node touch at least one edge of the selected relation type"**.
   - Then, **critically**: `links = data.links.filter((l) => visibleIds.has(source) && visibleIds.has(target))` (`types.ts:219`) — this keeps **every** edge between two surviving nodes, regardless of that edge's own `edgeType`.

**Confirmed logic defect (root cause of "relation filters reported as nonfunctional"):** the relation filter is implemented as a **node inclusion filter by incidence**, not an **edge filter**. Concretely: if work `W` has both a `cites` edge to reference `A` *and* an `influences` edge to the *same* reference `A` (two separate `graph_edge` rows — plausible today, since citation-resolution and annotation-classification write independently and there is no cross-path dedup preventing two different `edgeType`s between the same pair, see §21.2's integrity finding above), then filtering "Relation: cites" will correctly keep `W` and `A` (both have a `cites` edge somewhere), but the surviving-edge filter at `types.ts:219` will **also** render the `influences` edge between them, because it never checks `l.edgeType` at all — only that both endpoints are visible. A user who selects "cites" would see a non-`cites` edge still drawn between two visible nodes, exactly matching the plan's own description of the reported symptom. This also means the "1 of N shown" node count (`GraphView.tsx:361`) can be accurate while the edge set drawn underneath is not what the filter promised.

**Everything else on 21.3's requirement list, checked against the current code:**

- ✅ **Clear-all** — no dedicated "clear all filters" control exists at all (only per-select "All" options); a user must reset every dropdown individually. Gap.
- ✅ **Deep-linked filter state restores after reload** — confirmed via `graph.spec.ts:88-95` (Kind filter) and `:124-128` (Credibility filter), both explicitly reload and re-assert; this part works.
- ✅ **Accessible table exactly matches** — true by construction, since both consume `filtered` (§21.1).
- ❌ **"Multiple relation filters have defined OR/AND semantics displayed in the UI"** — there is only a single-select `relation` filter (one value at a time), not multiple simultaneous relation filters, so there is no OR/AND semantic to display at all; the requirement as written presumes a multi-select control that doesn't exist yet.
- ✅ **Filters do not mutate source data** — confirmed; `filterGraphData` returns a new `{ ...data, nodes, links }`, `data` state itself is never reassigned by filtering.
- ⚠️ **"Uploaded-work anchors remain visible unless Works visibility is disabled"** — partially true via **pinning** (`pinnedWorkIds`, `types.ts:201, 208`), which is an explicit opt-in the user must check per work (`GraphView.tsx:365-378`), not a default/automatic invariant. An unpinned uploaded-work node is filtered out like any other node the instant any filter excludes it (e.g., filtering `type=concept` hides all `work` nodes unless pinned — reproduced directly in `graph.spec.ts:238-246`, which is the *pinning* test, not a default-visibility guarantee). This is a real gap against the plan's DoD line "Uploaded works remain visible under all non-work-exclusion filters" (21.12) — today they are only guaranteed visible if the user has remembered to pin them.
- **Tests assert node/edge IDs, not just checkbox state** — `graph.spec.ts` already does this well (e.g. `:82-95`, `:117-127`) by checking `data-graph-node` presence/absence, which is exactly the pattern 21.3 asks for. Good precedent to extend to a real relation-filter-edge-type test, which does not exist today (no test asserts that a *specific edge* — as opposed to a *node* — disappears under the relation filter; this is precisely why the defect above went undetected).

## 4. Phase 21.4 — Node and label scaling

**This is the single most complete gap found in the audit: there is currently zero camera-distance-aware scaling of any kind.**

Evidence, `KnowledgeGraph3D.tsx`:

- Node radius: `NODE_SIZE[node.type]` (`:21-29`, a fixed lookup table by entity type) `+ pin/selected offsets` (`:172, 244`) — a pure function of node type and selection state, **never of camera distance**.
- Label scale: `const labelScale = Math.max(20, Math.min(42, 16 + node.label.length * 0.45));` (`:206`) — a pure function of **string length**, again never of camera distance. This line is the entirety of the plan's requested "clamp(min, computed, max)" pattern already present in spirit (`Math.max`/`Math.min`), but the *input* being clamped is wrong: it clamps label-length-derived size, not zoom-derived size.
- No camera-position/zoom listener exists anywhere in the component. `fgRef.current?.cameraPosition(...)` is only ever *written to* (on click, `:282-286`; on reset, `:216`), never *read* on an ongoing basis to drive label/node scale. There is no `onEngineTick`, no `requestAnimationFrame` loop, no throttled camera-distance sampling of any kind.
- No density-aware label hide/show, no "hide secondary label before shrinking primary" logic (there is only ever one combined two-line sprite per node — title line + type/state line, `:194-201` — with no separate on/off toggle for the second line).
- Billboarding (front-facing, non-mirrored) **is** correctly satisfied via `THREE.Sprite` (`:205`), which always faces camera by construction — this part needs no repair.
- High-contrast backing **is** present (`:190-192`, a fixed dark rounded rect behind white text) — satisfies the "readable backing/halo" requirement, though it is not re-evaluated per theme (always dark-on-white regardless of light/dark app theme; not flagged as a defect since a floating in-scene label chip conventionally uses a fixed treatment, but worth the implementers double-checking against the design system).
- Minimum clickable/tappable hit area — moot today since nothing shrinks, but will need an explicit floor once distance-based scaling is added (the plan's own requirement anticipates this).

**Node caching / performance implication that compounds this (relevant to both 21.4 and 21.10):** `nodeThreeObject` is a `useCallback` with dependencies `[pinnedWorkIds, selectedNodeId, typeColors]` (`:170-212`). `react-force-graph-3d` treats a changed `nodeThreeObject` function identity as "regenerate every node's ThreeJS object." Since `selectedNodeId` changes on **every node click** (`GraphView.tsx:105-108` → `onNodeClick` → `setSelected`), **every click anywhere in the graph currently forces the library to rebuild the sphere mesh + canvas-texture sprite for every single node in the visible graph**, not just the clicked one. This directly contradicts 21.10's "cached 3D objects... rather than recreating them every frame" guidance (worse: recreated on every *selection*, not merely every frame) and will compound badly once per-frame distance scaling is added on top, unless the implementation separates "which node is selected" (a per-node visual accent, ideally handled via a color/outline accessor instead of full object identity) from "what the object itself looks like."

## 5. Phase 21.5 — Edge visibility, scaling, and embedded labels

**Zero edge labels are rendered in the 3D scene today.** Evidence, `KnowledgeGraph3D.tsx`:

- The `ForceGraph3D` element (`:222-290`) sets `linkColor`, `linkWidth`, `linkDirectionalParticles`, `linkDirectionalParticleWidth/Speed/Color` — **no `linkThreeObject`, `linkThreeObjectExtend`, `linkLabel`, or any equivalent prop is set anywhere in the file.** `grep -n "linkThreeObject\|linkLabel" apps/web/src/components/graph/KnowledgeGraph3D.tsx` returns nothing.
- A relation's human-readable meaning is visible **only** in two places: (a) hovering shifts non-connected edges to a faint color (`:247-253`) but does not add any text; (b) clicking a link opens `GraphInspector`'s `selectedLink` branch (`GraphView.tsx:479-490`), which is a **click-through, sidebar-only** disclosure, not "on or within the connection line" as 21.5 requires.
- Edge width is a **fixed binary**, not zoom-scaled: `linkWidth={... connected ? 1.6 : 0.5}` (`KnowledgeGraph3D.tsx:254-259`) depends only on hover-adjacency, never on camera distance.
- Direction is conveyed only via directional particles (`linkDirectionalParticles={effectsEnabled ? 2 : 0}`, `:260`), which are disabled entirely once `effectsEnabled` is false (reduced motion, hidden tab, or graphs over 140 nodes, `:168`) — meaning **direction becomes completely illegible** (no arrowheads, nothing) for exactly the large-graph and accessibility-preference cases where legibility matters most. No `linkDirectionalArrowLength`/`linkDirectionalArrowRelPos` (the static-arrowhead alternative `react-force-graph-3d` supports) is used anywhere as a fallback.
- Relation colors **do** correctly use the shared relationship-family palette (`EDGE_FAMILY_META`, resolved to CSS vars, `:104-107, 247-252`) — this part is already right.
- **Color is not the only cue for edge *type* today, but only barely**: the family-level grouping (5 buckets: reference/influence/opposition/structural/prerequisite, `types.ts:97-116`) is coarse, and within the "influence" bucket specifically, several structurally distinct relation types collapse into one indistinguishable color+width+particle treatment with no other distinguishing visual signal at all (see next finding).

**`edgeFamilyFor()`'s keyword-matching coverage is incomplete relative to the real edge-type vocabulary, which undermines "use the existing relationship-family palette" (new finding):**

`types.ts:109-116`:
```
if (normalized.includes("outline") || normalized.includes("section")) return "structural";
if (normalized.includes("prerequisite") || normalized.includes("presupposes")) return "prerequisite";
if (normalized.includes("disagrees") || normalized.includes("criticizes") || normalized.includes("polemical")) return "opposition";
if (normalized.includes("cites") || normalized.includes("quotes") || normalized.includes("reference")) return "reference";
return "influence"; // default
```
Cross-referenced against every real edge-type string actually produced:
- The 14-value `edgeTypeEnum` (`schema.ts:478-493`): `responds_to`, `translates`, `is_edition_of`, `is_comparable_to`, `is_recommended_by` all fall through to the **default** `"influence"` bucket — none of their keywords are matched. `responds_to` in particular is arguably closer to "opposition" or "reference" than generic "influence."
- The dynamic `` `${workRole}_of` `` relation types from `edition_relation` (`apps/worker/src/analyze.ts:1756` — produces strings like `review_of`, `translation_of`, `edition_of`, `excerpt_of`): **none** match any keyword (the `_of` suffix isn't checked), so a review-of-a-book edge, a translation-of edge, and a "the work influenced this other work" edge are all rendered in the **identical** color/width/particle treatment today, despite being semantically very different relationships that the legend claims to distinguish.
- `discovered_source` (the literal fallback edge type at `graph.ts:481` when a source has no matched relation row) also falls to default `"influence"`.

This is a legend-accuracy defect, not merely a scaling one: the 21.5 requirement "Relation colors must use the existing relationship-family palette" is satisfied mechanically (every edge does get *a* family color) but not *correctly* — most of the actual edge-type vocabulary silently defaults into the same bucket as true influence/agreement relationships.

## 6. Phase 21.6 — Selection focus behavior

Trace of what "select a node" currently does, `KnowledgeGraph3D.tsx:271-288` (`onNodeClick`) and `GraphView.tsx:105-108`:

1. ✅ **Camera moves to frame the node** — `fgRef.current.cameraPosition(...)` with a damped 700ms transition (`:282-286`), satisfying requirement (1).
2. ✅ **Selected node stays visually prominent** — `radius` gets a `+1` bump when `selectedNodeId === node.id` (`:172, 244`).
3. ❌ **"Show only its most direct one-hop connections at full opacity... fade all unrelated nodes/edges into the background"** — **this exists in the code, but is wired to the wrong state.** `highlightNodeIds` (`:164-167`) — the mechanism that dims non-neighbors (`nodeColor`, `:229-237`) and dims non-connected edges (`linkColor`, `:247-253`) — is derived from `hoverNode`, **not** `selectedNodeId`/`selected`. `hoverNode` is set by `onNodeHover` (`:271`), which fires on mouse-over and **clears the instant the pointer leaves the node** (`onNodeHover(null)` on hover-out is the library's default behavior for this prop). Consequence: clicking (selecting) a node does **not** persistently fade unrelated content — only *actively hovering* does, and that fade vanishes as soon as the user's mouse moves away from the node they just clicked, which is almost immediately, since moving the mouse toward the inspector panel to read the details is the very next thing a user does. This is a direct, concrete violation of 21.6 requirements 3–5, and it is very plausibly the literal defect a real user would describe as "selecting a node doesn't focus it."
4. ❌ **Inspector/table focus state** — the inspector *does* update on selection (`GraphInspector`, driven by `selected`) and the table row gets `data-selected`/`aria-current` (`GraphAccessibleFallback.tsx:127-129`) — this part is correct.
5. ❌ **"Provide a focus-mode toggle: Focus selected / Expand one additional hop / Return to full graph"** — **does not exist**. No such control anywhere in `GraphView.tsx`. The closest analog, `directConnections` (`GraphView.tsx:165-175`), is a **read-only list rendered in the inspector sidebar** — clicking an item in it re-selects that node (`GraphInspector`'s `onSelectNode`), it does not filter/expand the visible graph.
6. ❌ **Keyboard behavior (select focused table row via keyboard; move to previous/next connected node; Escape to clear focus; activate link to entity detail)** — **none of this exists**. `GraphAccessibleFallback.tsx` rows are only keyboard-operable via the nested `<button>` per row (a plain click-equivalent, `:134`); there is no `onKeyDown` anywhere in `KnowledgeGraph3D.tsx` or `GraphView.tsx`, no Escape handler to clear `selected`/`selectedLink` (only `GraphInspector`'s explicit "Close" buttons, mouse/Enter-on-button only), and no prev/next-connected-node traversal of any kind.
7. ❌ **"Expose focus state in the URL where practical"** — `selected`/`selectedLink` are plain `useState`, never synced to `searchParams` the way `filters`/`pinnedWorkIds` already are (contrast with `updateFilter`/`togglePinnedWork`, `GraphView.tsx:90-128`, which both call `router.replace`). Reloading the page after selecting a node loses the selection entirely — this is inconsistent with the rest of the same component, which already has a working URL-sync pattern to copy.
8. ✅ **"Preserve a clear route to reset" / "avoid destroying the user's current filters"** — selecting a node does not touch `filters` state at all (confirmed by reading `onNodeClick`, which only calls `setSelected`/`setSelectedLink`); a separate "Reset view" button exists (`GraphView.tsx:395`) that only resets the camera (`resetSignal`), not selection or filters — so nothing is destroyed, but there is also no single obvious "clear focus" affordance distinct from "reset camera" or the inspector's own per-item "Close" buttons.

## 11. Root-cause hypotheses and proposed repair order

1. **Fix the relation-filter edge leak first (D-21-1).** It is the smallest, most self-contained change (one added boolean clause in `filterGraphData`), it is very likely the literal defect behind the plan's "relation filters reported as nonfunctional," and every other repair in this list benefits from filters being trustworthy before layering scaling/labeling work on top.
2. **Fix selection focus (D-21-2) second**, for the same reason — it's the plan's other headline reported symptom ("broken... focus behavior"), it's a small, localized change (swap `hoverNode` for `selectedNodeId` as the fade driver, add a focus-mode toggle), and it unblocks writing the 21.6 keyboard-behavior tests cleanly on top of a working base.
3. **Fix the edge-accumulation data-integrity gap (D-21-6) before any UI/scaling work**, not after — if stale, contradictory edges can silently accumulate across reprocesses, every subsequent visual fix (labels, scaling, dedup) will be polishing a rendering of data that can already be wrong. This is also the only defect here with genuine data-correctness stakes (P1, matches the plan's own "materially incorrect scholarly output" P1 definition), so it should be treated as a Library/backend-adjacent fix, not deferred to "polish."
4. **Then connect the missing relation sources (D-21-7)** — `resource_role`/`passage_annotation` — before investing in per-edge-type visual polish (labels, scaling, family colors), since adding these sources changes the shape/volume of what needs polishing.
5. **Then do node/label/edge scaling and caching together (D-21-3, D-21-4, D-21-5)** — they share the same underlying mechanism (a per-frame or throttled camera-distance read) and the same underlying performance risk (recreating 3D objects too eagerly), so implementing them in the same pass avoids solving the caching problem twice.
