## Purpose

A web application that helps readers understand difficult scholarly works (philosophy, monographs, research articles) by automatically generating an interactive "critical edition": an annotated reader that surfaces explicit citations, implicit intellectual context, and secondary literature, and turns that into a personalized, priority-ranked reading roadmap. Serves both researchers working deeply in an established field and readers entering a field for the first time. Not a substitute for reading primary sources — every AI-generated claim carries confidence and provenance rather than being presented as settled scholarship.

Full product definition, worked examples (Heidegger, Vico), and the complete requirement inventory: [`docs/architecture/plan.md`](./docs/architecture/plan.md) §1–§2.

## Functional Requirements (summary — full detail in the plan)

- Upload and process scholarly texts (PDF, EPUB, TXT, Markdown in MVP; scanned/OCR PDF and DOCX phase-4-adjacent).
- Reader ("interactive critical edition"): original text + notes, AI- and user-generated annotations, highlights, bookmarks, search, adjustable typography, light/dark/distraction-reduced modes.
- Ten relationship categories for every recommendation (explicit reference, secondary-scholarly recommendation, historical/intellectual context, prerequisite, conceptual influence, disagreement/polemical target, interpretive aid, parallel/comparison, optional extension, AI-inferred), each with explanation, evidence, confidence, provenance, verification status.
- Personalized, dependency-ordered reading roadmap with priority tiers, manual overrides, concise/comprehensive modes, time/depth/expertise filters.
- Personal reading catalogue and knowledge profile (status, understanding ratings 0–100 with labels, chapter/section-level progress).
- Multi-work workspace: tabs, sidebar, split-pane reading across two works.
- **3D knowledge-graph visualizer** (added by explicit user request during planning): per-user, per-work and global, showing works/figures/concepts/traditions, read/unread status, and missing (referenced-but-unacquired) links, with a mandatory accessible table fallback.
- Auth, per-user data isolation, admin tooling, testing, accessibility (WCAG 2.2 AA), and privacy/copyright policy as detailed in the plan.
- **Phase 8 (repair + autonomous critical edition):** transform the app into a reliable, largely autonomous critical-edition generator — page-aware PDF extraction, automatic metadata, anchored authorial footnotes, explicit + implied reference resolution, credibility-aware research across scholarly/web/social sources, and traceable critical notes under a cost ceiling. (Redefined this session; supersedes the old "Phase 8 = Companion".)
- **Phase 9 (final):** build a fully independent educational companion site teaching this project's build, start to end.

## Architecture and Tech Stack

TypeScript throughout. Next.js (App Router) on Vercel (web UI + CRUD API routes + Auth.js) + a Node worker service on Render (pg-boss consumer: ingestion, OCR, citation extraction, AI relationship classification, bibliographic lookups, roadmap computation) + Supabase (Postgres + `pgvector` + Storage) as the shared system of record. AI: OpenAI + Anthropic behind a common provider-adapter interface, cheapest-tier-first routing. 3D graph: `react-force-graph-3d`. Full stack table, alternatives comparison, and text architecture diagram: plan §5–§8.

**Cost constraint (explicit, drives several choices below):** optimize for lowest cost at current single-user scale, on infra and AI-token spend equally; managed services (Vercel/Supabase/Render) stay as chosen rather than trading for self-hosting. Free tiers used everywhere realistically possible (Vercel Hobby, Supabase free, Sentry free, Resend free). The one recurring paid cost: Render's worker needs at least the ~$7/mo Starter instance, since a persistent job consumer can't run on Render's free (sleep-on-idle) tier — called out explicitly, not hidden. See plan §3/§5.

## Important Design Decisions and Rationale

| Decision | Rationale |
|---|---|
| Vercel + Supabase + Render, not AWS/GCP or self-hosted VPS | User-confirmed: lowest ops burden, still keeps growth headroom |
| Auth.js + own Postgres tables, not a managed auth vendor | Full control over verification/reset flows the brief requires; no vendor lock-in |
| OpenAI + Anthropic multi-provider from day one | User already holds OpenAI credits; wants flexibility, not to pay twice for the same call |
| `pgvector` in existing Postgres, not a dedicated vector DB | Brief explicitly says not to add a separate DB unless clearly justified |
| `graph_edges` generic table + recursive CTEs, not a graph database | Same reasoning; schema still supports a future graph-DB mirror if needed |
| pg-boss on Postgres, not Redis/BullMQ | One fewer service to operate and pay for |
| ScholarLens (github.com/aakashshahani/ScholarLens) — ideas only, zero code reuse | No LICENSE file exists in that repo (`gh api .../license` → 404, `license: null`) despite an MIT badge image with no actual license text; treated as all-rights-reserved |
| 3D knowledge-graph visualizer added, reconciled with "avoid excessive 3D" | That instruction targeted decorative landing-page chrome (explicit contrast with ScholarLens); this is one deliberate, opt-in, restrained data-viz tool behind login, with a mandatory non-3D accessible fallback |
| AI routing defaults to cheapest tier for every task, promoted only on eval-harness evidence | Explicit cost constraint — stricter than a generic cheap/expensive split |
| JWT session strategy + `users.sessionVersion` counter, not database sessions | Auth.js v5's Credentials provider requires JWT sessions — DB sessions only auto-wire for OAuth-adapter flows. Revocability (deviation from plan §14's literal wording) is achieved by checking `sessionVersion` in the `jwt` callback on every request and incrementing it to invalidate all outstanding JWTs (used on password reset); verified working end-to-end in Phase 1a testing. |
| Colima + Docker CLI for local Postgres, not Docker Desktop | No GUI first-run dialogs to accept — this session/sandbox can't interact with them |
| Node 24 (Active LTS), not the Homebrew-default Node 26 (Current) | More predictable support on Vercel/Render; explicit `brew uninstall node && brew install node@24` swap, pinned via `.node-version` and `package.json#engines` |
| Packages scaffolded when actually needed, not upfront | Deliberate deviation from the plan's Phase-1 "empty-but-wired" wording — creating unused stub packages ahead of the phase that needs them is premature scaffolding. Actual timeline: `packages/ingestion` (Phase 2), `packages/ai-adapters` + `packages/bibliographic` (Phase 4), `packages/roadmap` (Phase 5) — all built and in use. `packages/ui` still not created — reader/roadmap/graph components live in `apps/web`; it arrives only if a second app needs to share them |
| `packages/ingestion` created in Phase 2, not deferred to Phase 4 | Phase 2's own plan text calls for "first parser (text-layer PDF + plain text/Markdown)" — unlike the other deferred packages, this one was actually needed now, not speculative |
| Shared Supabase Storage access lives in `packages/ingestion`, not duplicated in `apps/web` and `apps/worker` | Both the upload route (web) and the parser (worker) need it; ~40 lines of real overlap was worth one shared module rather than two near-identical copies |
| `unpdf` (pdf.js-based) for PDF text extraction, not `pdf-parse` | Matches the plan's `pdf.js` choice; `pdf-parse` has a known footgun where a bare `require` can trigger test-file loading. `canvas` (pdfjs-dist's optional native dep for visual rendering) is explicitly *not* built — we only need text extraction, and compiling it would need system libs (cairo/pango) not present here |
| Local dev's upload/worker flow targets the **real** Supabase Storage bucket, not a local equivalent | No good local substitute without adding MinIO or similar; Storage is a hosted service either way. Test uploads during local dev must be cleaned up manually (same discipline as test DB users) since Storage isn't reset the way the local Postgres container is |
| Upload protection uses format/archive validation plus an optional private ClamAV adapter | PDFs and EPUBs are magic/manifest-validated with size and entry limits; when `CLAMAV_SCAN_URL` is configured a private scanner is required to return clean. Unconfigured deployments accurately describe this as content validation, never as a malware scan |
| Highlights anchored by a quote+prefix+suffix text-fingerprint, not raw DOM/page coordinates | Directly implements plan §25 risk R3 ("annotation position drift"). Coordinates break across re-renders (font-size change, reflow, PDF re-layout); a text-fingerprint re-locates the same passage by content instead, and works identically for both `TextReader` (paragraph DOM) and `PdfReader` (pdf.js text layer) since both are ultimately DOM text nodes at highlight-apply time. Verified surviving a full page reload in the Phase 3 Playwright suite, not just an in-memory check |
| pdf.js worker vendored as a static file rather than resolved via `import.meta.url` | Turbopack didn't reliably resolve pdfjs-dist's worker script that way in dev; a vendored copy in `apps/web/public/` sidesteps the resolution entirely at the cost of a manual re-copy step on every `pdfjs-dist` upgrade (tracked in Known Problems) |
| Footnote detection heuristic runs only for `text/plain`/`text/markdown`, not PDF | PDF footnote extraction needs layout/structure awareness (page-bottom positioning, font-size cues) that the current plain-text-only extraction pipeline doesn't have; scoped out explicitly rather than attempted half-working. Tracked in Remaining Tasks, not silently dropped |
| Split Playwright coverage into a CI-safe subset plus a manually run full-stack suite | CI runs landing/onboarding accessibility and the authorization matrix against web + Postgres. Reader, analysis, roadmap, and graph flows also need the worker, Supabase Storage, and/or live bibliographic/AI APIs, so those remain serialized (`workers: 1`) and manually run as a full-stack acceptance suite. This keeps every push deterministic without pretending the external-service flows are covered by CI. |
| LLM providers (`packages/ai-adapters`) implemented over plain `fetch`, not the OpenAI/Anthropic SDKs | No SDK dependency to install/build (some have native/postinstall steps); the adapter surface the plan §11 requires is tiny (`complete()`), so a thin fetch client is less code *and* less supply-chain surface than pulling two vendor SDKs. Business logic only ever sees the `LLMProvider` interface — no vendor import anywhere in the app |
| Deterministic **heuristic classifier** as the fallback when no AI key is configured | Same pattern as Phase 1's `ConsoleMailProvider`: rather than blocking the whole analysis pipeline on API keys the user hasn't provided yet, the pipeline runs end-to-end against a deterministic keyword-rule stub. Every annotation it produces is flagged `heuristic`/`promptVersion: "heuristic"` all the way to the UI (which shows "Heuristic (no AI key)") so it is never presented as a real model verdict. Keeping it deterministic also makes it unit-testable without a network |
| Cost-first AI routing: every task defaults to the cheapest model tier, promoted only on eval evidence | Direct implementation of the explicit cost constraint (plan §3/§11) — stricter than a generic cheap/expensive split. Model IDs are env-overridable (`OPENAI_MODEL_CHEAP`/`ANTHROPIC_MODEL_CHEAP`) so a catalog change needs no code edit. Every call (including the heuristic, logged at $0) is written to `ai_usage_logs` for the future cost dashboard |
| Anti-hallucination: bibliographic facts come only from a real lookup, never the LLM | A citation's title/author/year/DOI is only ever set from a Crossref/OpenAlex/Open Library match (`packages/bibliographic`), with a title-overlap confidence guard so a citation is never attached to a wrong record; an unmatched citation stays `unresolved` rather than guessed. The LLM only classifies the *relationship*, never invents the reference (plan §11/§12 R1) |
| Annotation anchors reuse the highlight text-fingerprint; inline markers are single-point insertions, not range wraps | Anchoring by quote+prefix+suffix (same as highlights, plan §25 R3) so a marker re-locates across re-render. Markers are inserted as a single clickable superscript at the anchor start rather than wrapping the passage, so the AI-annotation layer and the user-highlight layer never fight over overlapping DOM ranges. Text/Markdown only — PDF page anchoring needs positional data the merged-text extraction lacks, so PDF annotations are work-level (panel only), a documented limitation |
| Analysis enqueued on metadata-confirm (work → ready), on a separate `analyze-work` queue | A slow or failed analysis must never block the reader from opening a document whose text already extracted fine (separate queue). Confirming is the natural trigger (metadata is user-verified by then, plan §23), with a manual `/analyze` re-trigger as the recovery path; re-runs are idempotent (clear prior *system* output, keep user edits) |
| `bibliographic_records` treated as an append-only shared catalog, deduped by DOI/external id | Matches the plan §9 shared-canonical-catalog direction and avoids duplicate records across re-analyses. Trade-off: a record can be orphaned when the works citing it are deleted (no user FK to cascade). Acceptable at single-user scale; a periodic orphan sweep is the eventual cleanup (noted in Known Problems) |
| Roadmap computed on demand each request, not stored as a `reading_roadmaps`/`roadmap_items` snapshot | Deviation from plan §9's literal shape. A persisted snapshot drifts the instant analysis re-runs or a rating changes; recomputing from the graph + saved profile/overrides means "recalculation respects overrides" is automatic and there's no stale state to invalidate. Only durable user-authored state is stored (`reading_records`, `understanding_ratings`, `roadmap_overrides`) |
| Pure ranking (`@ice/roadmap`) split from the DB traversal (`apps/web/src/lib/roadmap.ts`) | The plan's Heidegger/Vico cases are acceptance tests (§13 step 9); keeping `rankRoadmap` a pure function of (candidates, profile, overrides, options) makes them deterministic Vitest units with no DB. The web lib does only the recursive-CTE traversal + profile/override fetch, then calls the pure ranker |
| Roadmap transitivity is realized by re-entering the graph through matched owned works | Analysis only writes work→bibliographic_record edges, so a bib record has no outgoing edges unless the user also uploaded that work. The recursive CTE follows a reached record to another owned work by **normalized-title match**, then continues from its edges — so "Kant → Hume" surfaces only when Kant is itself in the library. Honest about what single-user data supports (documented limitation), degrades to a leaf otherwise |
| 3D graph via `react-force-graph-3d`, dynamically imported (`ssr: false`), with a **mandatory** accessible table as the default view | Matches plan §5's library choice and §20's fallback requirement. The WebGL scene can't be read by assistive tech, so the sortable/filterable/keyboard-operable table is the default and the equal — the 3D view is an opt-in enhancement. Restrained per §19: no auto-rotation, palette colors resolved from CSS vars (re-resolved on theme change), no forced motion |
| "Missing link" = a referenced `bibliographic_record` with no owned work matching it (normalized title) | Directly implements plan §9's missing-link definition. The graph node state is `read`/`reading`/`unread`/`missing`/`primary`, computed per-user from `reading_records` + `understanding_ratings` + the in-library match, which is what makes each user's graph their own |

Full rationale for every stack choice, including rejected alternatives: plan §4–§6.

## Known Problems and Technical Debt

- Documented (not a bug): `CLAUDE.md`/`Claude.md` cannot coexist as separate files on this machine (case-insensitive filesystem) — see the note at the top of this file.
- **Git push hangs (environment gotcha):** plain `git push`/`git ls-remote` over HTTPS hangs indefinitely because the system-level `osxkeychain` git credential helper (`/opt/homebrew/etc/gitconfig`) waits on a GUI keychain-unlock prompt that never appears in this sandbox. Workaround: `git -c credential.helper= -c credential.helper='!gh auth git-credential' push origin main` — **both** `-c` flags are required: `credential.helper` is a cumulative list-type config, so `-c credential.helper='!gh auth git-credential'` alone just *adds* a helper without removing the system-level `osxkeychain` entry, which still runs first and hangs (or returns a stale/wrong token). The first `-c credential.helper=` (empty value) clears the inherited list; the second one then adds only the `gh`-backed helper. `gh` commands (e.g. `gh repo create --push`) are unaffected by any of this.
- **Pushing changes to `.github/workflows/*.yml` needs the `workflow` OAuth scope**, which `gh`'s default token doesn't have. One-time fix: `gh auth refresh -h github.com -s workflow` (interactive — opens a device-code browser approval). Without it, the push is rejected with "refusing to allow an OAuth App to create or update workflow ... without workflow scope", even though the same push works for every other file.
- **`docker compose` plugin isn't found by default after `brew install docker-compose`:** Homebrew's Docker CLI doesn't look in `/opt/homebrew/lib/docker/cli-plugins` unless told to. Fix (already applied, `~/.docker/config.json`): add `"cliPluginsExtraDirs": ["/opt/homebrew/lib/docker/cli-plugins"]`.
- **Service CLI authentication uses device/browser approval and secure local credential stores, never repo files.** GitHub, Supabase, Vercel, and Render CLI sessions were all restored and verified on 2026-07-18. Supabase's device flow may print a short verification code that must be entered back into the CLI/browser; its resulting token is stored in macOS Keychain. If any session expires, rerun that tool's supported login/device flow or use a narrowly scoped per-command token, but never put token values in this file, shell scripts, `.env.example`, commits, or command output.
- **Render needs a GitHub connection made through its dashboard before it can fetch even a repo the user already owns** — `render services create --repo ...` fails with "invalid or unfetchable" until GitHub is explicitly connected under Render's Account Settings → Connected Accounts (an OAuth step, done by the user; no CLI equivalent found). This is a different model from Vercel, whose CLI uploads local files directly and doesn't need this step to deploy via CLI.
- **Render requires a payment method before creating *any* paid-plan service, not just at billing time** — `render services create --plan starter` fails with HTTP 402 ("Payment information is required") until a card is added under Render's dashboard billing page, even though the free tier exists for other service types. Confirms the plan's own prediction that Render's worker is the one cost in this stack that isn't $0.
- **`render services update` has no way to set environment variables** — despite the CLI's `create` command accepting `--env-var`, there's no equivalent on `update`, and env vars weren't set at creation time here. Used the REST API directly instead: `PUT https://api.render.com/v1/services/:id/env-vars` with a JSON array of `{key, value}` objects (replaces the full set, not additive).
- **`tsx --env-file=.env` crashes if `.env` doesn't exist** — fine for local dev (where the file exists) but fatal on any platform that injects env vars directly instead of via a file (Render, and likely most others). `tsx --env-file-if-exists=.env` (Node's own `--env-file-if-exists` flag, available in Node 24) degrades gracefully instead — verified locally both with and without the file present before relying on it in production.
- **pnpm's global bin dir isn't on PATH by default** (`pnpm add -g` fails with "configured global bin directory ... is not in PATH"). One-time fix: `pnpm setup` (writes `~/.zshrc`), but since this environment's Bash tool doesn't source shell rc files between commands, every command needing a pnpm-global binary (e.g. `vercel`) must still `export PNPM_HOME="$HOME/Library/pnpm"; export PATH="$PNPM_HOME/bin:$PATH"` inline.
- **Vercel + pnpm monorepo: deploying from the app subdirectory silently breaks the build.** Running `vercel link`/`vercel --prod` from inside `apps/web` uploads only that subtree, so Vercel never sees the root `pnpm-lock.yaml`/`pnpm-workspace.yaml` and falls back to `npm install` (which then fails on the workspace-only `@ice/db` dependency). Fix: set the Vercel project's **Root Directory** to `apps/web` (no CLI flag for this — used `vercel project update` first, which lacks a root-directory option, then the REST API: `PATCH /v9/projects/:id?teamId=...` with `{"rootDirectory":"apps/web"}`), then deploy **from the repo root** so the whole monorepo — including the root lockfile — gets uploaded and Vercel `cd`s into Root Directory to build.
- **Vercel REST API calls need the *actual* `orgId`, not a value hand-transcribed from a JWT.** A `PATCH` to `/v9/projects/:id?teamId=...` returned "Not authorized" using a `teamId` misread from the `VERCEL_OIDC_TOKEN` payload (visually similar-looking ID, one character off). The authoritative value is in `.vercel/project.json` (`orgId`) written locally by `vercel link` — use that, not a manually parsed token.
- **The Supabase DB password is auto-generated and not recoverable** — it was generated with `openssl rand` during project creation and passed straight to `supabase projects create --db-password`; Supabase never displays a project's DB password again after creation (by design). It was surfaced to the user once, out-of-band, right after creation. If it's ever needed again and lost, reset it via Supabase Dashboard → Project Settings → Database → Reset Database Password, then update `DATABASE_URL`/`DIRECT_URL` in Vercel (`vercel env rm` + `vercel env add`) and redeploy.
- **pnpm blocks postinstall scripts by default:** new dependencies with native/build postinstall steps (seen so far: `sharp`, `unrs-resolver`, `esbuild`; also `canvas`, deliberately left *unbuilt* — see Design Decisions) need explicit approval or `pnpm install` aborts with `ERR_PNPM_IGNORED_BUILDS`. Approve/deny in `pnpm-workspace.yaml` under `allowBuilds:` (not `package.json#pnpm` — that field is no longer read by this pnpm version). Review each new one on its merits; don't rubber-stamp.
- **Route protection resolved in Phase 2** (superseding the Phase 1 note that used to be here): centralized via `requireSession()` (pages — redirects to `/login`) and `getApiUserId()` (API routes — returns `null` for the caller to turn into a 401) in `apps/web/src/lib/auth.ts`, used by the `(app)` layout and every protected route instead of ad hoc `auth()` calls. Still Node-runtime, not Edge middleware, for the same `sessionVersion`/`postgres.js` reason as before.
- **`next-auth`/`@auth/drizzle-adapter` pin conflicting `@auth/core` versions (0.37.2 vs 0.41.2), and this silently breaks `Session` type augmentation.** Without a fix, TypeScript treats the two copies as unrelated modules, so `declare module "@auth/core/types" { interface Session {...} } ` in `auth.d.ts` patches whichever copy TS resolves for *that file*, which isn't reliably the same copy `next-auth`'s own `auth()` return type uses elsewhere — `session.user.id` silently stays `string | undefined` in consuming files with no error pointing at the real cause. Forced a single version via `pnpm-workspace.yaml`'s `overrides: { "@auth/core": 0.37.2 }` (pinned to next-auth's own version, since that's what its runtime was tested against). Even after the override, augmentation remained unreliable at some call sites for reasons not fully run to ground — worked around at the application level instead (see the route-protection entry above and the `requireSession()`/`getApiUserId()` helpers), which also removed a lot of repeated auth-check boilerplate, so it's a net improvement rather than a pure workaround.
- **TypeScript's `incremental: true` cache (`tsconfig.tsbuildinfo`) can hide the effect of a type-only change** (module augmentation edits, `.d.ts` changes) across `tsc --noEmit` runs, showing stale errors/non-errors from before the edit. `*.tsbuildinfo` is gitignored (never committed) but persists locally — if a typecheck result looks suspicious after editing types specifically, `rm apps/web/tsconfig.tsbuildinfo` before re-running.
- **pg-boss v10 requires `boss.createQueue(name)` before `send()`/`work()` on that queue** — older pg-boss auto-created queues on first `send()`; v10 does not. Skipping this doesn't throw — `send()` succeeds but the job silently lands nowhere usable (observed: it registered against an unrelated internal `__pgboss__send-it` queue instead), so the worker never picks it up and there's no error anywhere to point at the cause. Fixed in `packages/db/src/queue.ts`'s `getQueue()`, which now calls `createQueue(QUEUE_EXTRACT_TEXT)` once during startup before returning the boss instance.
- Trivial, non-blocking CI annotation: `pnpm/action-setup@v4` is flagged by GitHub as targeting a deprecated Node 20 runner internally (it still runs fine, forced onto Node 24). Bump to a newer major when one addresses this.
- **`apps/web/public/pdf.worker.min.mjs` is a vendored, hand-copied file, not a build-time dependency resolution** — copied once from `node_modules/.pnpm/pdfjs-dist@4.10.38/.../pdf.worker.min.mjs` because Turbopack didn't reliably resolve pdfjs-dist's worker via `new URL(..., import.meta.url)`. This means **it will silently go stale on a `pdfjs-dist` version bump** (the app keeps working against the old worker version, which can drift from the main-thread library version in ways that are hard to diagnose) — re-copy this file by hand any time `pdfjs-dist` is upgraded.
- **Only the CI-safe Playwright subset runs on every push.** Landing/onboarding accessibility and the authorization matrix run in CI; reader, annotations/analysis, roadmap, and graph specs need the worker, Supabase Storage, and/or live external APIs and remain manual. A green CI run therefore proves the deterministic subset, not every interactive/external-service flow; run the full serialized suite before major releases.
- **E2E test fixtures must clean up Supabase Storage explicitly, not just DB rows** — `documents.storage_path` has no FK-level relationship to the actual Storage object, so a cascading DB delete (`onDelete: cascade` on `user_id`) never removes the underlying file. `apps/web/e2e/helpers.ts`'s `deleteTestUser` now does this explicitly (see Phase 3 Completed Tasks); any *new* test fixture that uploads a file must follow the same pattern or it will leak Storage objects indefinitely.
- **Adding a workspace package/dependency requires committing `pnpm-lock.yaml` too** — obvious in hindsight, but `git add packages apps` does NOT stage the root `pnpm-lock.yaml`, so a commit that adds a package (e.g. `@ice/observability` in Phase 7) can pass local checks yet break CI's `pnpm install --frozen-lockfile` with `ERR_PNPM_OUTDATED_LOCKFILE`. Always `git add pnpm-lock.yaml` alongside a package.json change.
- **Footnote heuristic is pattern matching, not layout-aware extraction** (documented in the function's own doc comment) — it won't catch every citation style, and doesn't run on PDFs at all yet (only `text/plain`/`text/markdown`, see Remaining Tasks). A single trailing numbered line is enough to be considered (no minimum run length), which was a deliberate fix this phase — see the Phase 3 Completed Tasks entry for the false-negative bug this corrected.
- **Vercel stores `DATABASE_URL`/`DIRECT_URL` as *Sensitive* env vars, so `vercel env pull` returns a ~13-char placeholder, not the real connection string** (discovered Phase 4). Sensitive vars are write-only — they decrypt only at build time, never back through the CLI/API. Consequence: the documented `vercel env pull` → run-migration path does **not** work for these. Phase 4's production migration was instead applied via the **Supabase Management API** SQL endpoint (`POST https://api.supabase.com/v1/projects/:ref/database/query`, Bearer = the Supabase access token — no DB password needed). When doing that, also insert the drizzle bookkeeping row so future `drizzle-kit migrate` stays consistent: `INSERT INTO drizzle.__drizzle_migrations (hash, created_at) VALUES ('<sha256 of the raw .sql file>', <the entry's "when" from meta/_journal.json>)` — drizzle gates by the `created_at` timestamp, so this is what marks the migration applied.
- **The Supabase Management API is behind Cloudflare, which blocks default library User-Agents** (Python `urllib` → HTTP 403 "error code: 1010"). Use `curl` (its UA passes) with `--data-binary @file.json` to avoid both the UA block and shell-quoting hell on the SQL payload. Build the JSON body with a Python heredoc writing to a file, then `curl` that file.
- **Auto-mode classifier blocks production DB writes** (Phase 4): direct writes to the production database (the migration, and seeding/tearing-down verification data) are denied by the auto-mode safety classifier and require explicit per-action user approval (or a Bash permission rule). Reads (schema/state queries) go through. This is a guardrail, not a bug — surface the intended write to the user and let them approve, exactly as done for the Phase 4 prod migration and end-to-end verification.
- **OpenAI is configured and live; Anthropic remains optional.** `OPENAI_API_KEY` is present in the encrypted production environment and a real `gpt-4o-mini` adapter call was verified on 2026-07-18; the value is not retrievable from or stored in git. The Anthropic adapter remains available but has not been exercised with a live key. The deterministic heuristic remains the explicit fallback whenever no provider key is available and is still labeled honestly in the UI.
- **Invalid-password login — FIXED (Phase 8.1).** Root cause: Auth.js v5 `signIn` **throws** a `CredentialsSignin`/`AuthError` when `authorize()` rejects (it does not return `{ error }`), so `loginAction`'s old `if (result?.error)` branch was never reached and the throw surfaced as an unhandled runtime error. Fix: `loginAction` now wraps `signIn` in try/catch, redirects `AuthError` → `/login?error=1` (the login page already renders the friendly message), and re-throws everything else — crucially the `NEXT_REDIRECT` thrown by `redirect()`, which must propagate. Kept as a note so the pattern isn't reintroduced.
- **`bibliographic_record` rows orphan on work/user deletion** — they're a shared, append-only catalog with no user FK, so a cascading user delete leaves them behind (Phase 4 verification cleaned them explicitly with a `not exists` sweep). A periodic orphan-cleanup job is eventual work; harmless at single-user scale.
- **`ai_usage_log.document_id` is `ON DELETE SET NULL`, not cascade** — deleting a document nulls the link rather than removing the usage row (usage/cost history should outlive the document per plan §22). So account/document deletion leaves usage rows with a null `document_id`; clean them explicitly if a full purge is wanted (Phase 4 teardown deleted this doc's rows first).
- **drizzle expands a JS array in a raw `sql` template to a param LIST `($1, $2)`, not a single array param** (Phase 5) — so `br.id = ANY(${ids})` fails with "op ANY/ALL (array) requires array on right side" (`ANY(($1,$2))` is invalid), and even `ANY(${ids}::uuid[])` fails (`(($1,$2))::uuid[]` casts a tuple). Use `br.id IN ${ids}` instead, which becomes the valid `IN ($1, $2)`. This silently returned empty roadmaps/graphs until fixed — guard for a non-empty array first (an empty one produces `IN ()`, a syntax error). Prefer the drizzle `inArray()` helper in non-raw queries.
- **E2E suite must run serialized (`workers: 1`)** (Phase 5) — the specs all drive uploads through ONE shared local worker, and since Phase 4 each upload enqueues live-API analysis. Running spec files in parallel (Playwright's default) piled concurrent analysis jobs on that worker and starved text extraction, causing extraction waits to time out. `workers: 1` in `playwright.config.ts` keeps queue depth sane; extraction waits are 45s and the test timeout 120s to absorb the residual live-API latency. The annotations spec still occasionally needs its one retry (first analysis job + worker warmup); that's expected, not a regression.

## Database and API Decisions

- **ORM:** Drizzle ORM + `drizzle-kit` (native `pgvector` column support).
- **Full domain schema:** see plan §9 for the eventual table list — rolls in incrementally, one migration set per phase, never all at once.
- **Phase 1 schema:** `user` (includes `password_hash`, `session_version` beyond the Auth.js default shape), `account`, `session`, `verification_token`, `password_reset_token`. Migrations `0000_luxuriant_risque.sql`, `0001_mighty_kylun.sql`.
- **Phase 2 schema (simplified subset of plan §9 — see Design Decisions for why):** `work` (title, author_name as plain text, work_type), `edition` (edition_label/translator/publisher/year/isbn/doi, all nullable), `document` (storage_path, mime_type, file_size, processing_status enum, extracted_text/title/author, processing_error), `processing_job` (job_type, status enum, error, attempts, pg_boss_job_id). Migration `0002_colossal_zarda.sql`.
- **Phase 3 schema:** `document.last_position` (jsonb, nullable — reading-position resume state); `footnote` (document_id, marker, content); `highlight` (user_id, document_id, anchor jsonb [quote+prefix+suffix text-fingerprint, not coordinates — see Design Decisions/R3], color); `note` (user_id, document_id, highlight_id nullable [standalone vs. highlight-attached], body); `bookmark` (user_id, document_id, position jsonb, label). Migration `0003_broad_blade.sql`.
- **Phase 4 schema:** `bibliographic_record` (source, external_id, title, authors, year, doi, url, access_status enum, raw jsonb — shared append-only catalog); `citation` (document_id, raw_text, resolved_bib_id nullable, resolution_source); `annotation` (user_id, document_id, relationship_category enum [the 10 categories], target_bib_id nullable, target_label, anchor jsonb [same fingerprint shape as highlights], extracted_source_text, explanation, confidence real 0–1, model_used, prompt_version, created_by enum, verification_status enum, hidden); `graph_edge` (user_id, source_type/id, target_type/id, edge_type enum [14-value vocabulary], weight, confidence, evidence, created_by — generic typed edge for Phase 5 roadmap traversal); `ai_usage_log` (document_id nullable `set null`, task, provider, model, prompt/completion tokens, estimated_cost_usd). Plus `document.analysis_status`/`analysis_error`. Migration `0004_real_anthem.sql`. Applied to production via the Supabase Management API (see Known Problems), not `drizzle-kit migrate` (the prod DB URL is a Sensitive Vercel var and can't be pulled).
- **Phase 5 schema:** `reading_record` (user_id, work_id nullable, bib_id nullable, status enum [planned/reading/completed/abandoned], started/finished_at); `understanding_rating` (user_id, work_id nullable, bib_id nullable, score int 0–100 [>=60 = "known" → roadmap deprioritizes]); `roadmap_override` (user_id, root_work_id, bib_id, hidden, manual_tier enum nullable, manual_position int nullable, added_manually). Plus `reading_status`/`priority_tier` enums. Migration `0005_lazy_black_knight.sql`, applied local + production (Management API). A "target" is polymorphic — exactly one of work_id/bib_id set. No roadmap-snapshot tables (computed on demand — see Design Decisions).
- **Phase 6 schema:** `user.preferences` jsonb (nullable) — `{ expertise?, onboardedAt? }`; `onboardedAt` presence marks onboarding complete (gates the `/welcome` redirect), `expertise` seeds the roadmap's default level. Migration `0006_aromatic_yellow_claw.sql`, applied local + production. The Auth.js DrizzleAdapter ignores this extra column, so no adapter changes were needed.
- **Phase 7 schema:** no new tables — migration `0007_robust_donald_blake.sql` adds 15 **indexes** on the hot filter/join columns (Postgres doesn't auto-index FKs): `graph_edge` (user_id+source_id, user_id+target_id — the roadmap CTE + centrality), per-document reader/analysis tables (`footnote`/`highlight`/`note`/`bookmark`/`citation`/`annotation`/`processing_job` by document_id), `work`/`document` by owner, and the Phase 5 profile tables by user. Applied local + prod.
- **`@auth/drizzle-adapter` quirk (recorded so it isn't rediscovered):** its `AdapterAccount` type requires specific snake_case JS object keys on the `account` table definition (`refresh_token`, `access_token`, `expires_at`, `token_type`, `id_token`, `session_state` — matching OAuth2 spec field names), not the camelCase Drizzle convention used elsewhere. This is a TS-level object-key requirement only; the actual DB column names are unaffected either way.
- **Job queue:** pg-boss on the same Postgres, two queues now (`extract-text`, `analyze-work`). Both explicitly `createQueue()`-d at startup (pg-boss v10 requirement — see Known Problems). Separate queues so a slow/failed analysis never blocks text extraction or the reader.
- **External APIs:** OpenAlex, Crossref, Open Library are **integrated and verified against the live services** (`packages/bibliographic`, keyless). The fetch-based OpenAI adapter is configured in production and verified with a real `gpt-4o-mini` call; the Anthropic adapter is implemented but not live-key tested. The heuristic fallback remains available and is labeled in provenance. Resend's console fallback is verified. Google Books, Semantic Scholar, real Resend delivery, and Sentry are not yet integrated/provisioned.
- **Production database is live**: Supabase project `interactive-critical-edition` (ref `vlrzvwswippuaitmrujz`), with the Drizzle migration ledger verified through `0007`. Local dev intentionally still targets local Docker Postgres for the database, but the **real** Supabase Storage bucket for file uploads (no good local equivalent) — a deliberate, asymmetric separation, not an oversight. Test uploads must be cleaned from both DB and Storage; the current manual-acceptance account/data are intentionally being retained only until the user finishes testing.

## Resuming Work After a New Claude Code Session

1. Read this file top to bottom — it reflects the actual current state, not the plan's aspirational state.
2. Read `docs/architecture/plan.md` for full architectural detail on whatever you're about to touch.
3. Check `git log --oneline -20` and the most recent tag (`git tag --list`) to see the last completed phase checkpoint.
4. Check "Remaining Tasks" above for the next unchecked item — work top to bottom within the current phase.
5. Before starting new work, confirm the working tree is clean (`git status`) and there's nothing uncommitted from a prior session.
6. After every meaningful step: update this file's Changelog, Completed/Remaining Tasks, and Current Implementation Status, then commit and push. Do not batch multiple days of undocumented work.
7. Never mark a phase complete in this file unless its tests pass and its Definition of Done (plan §23) is actually met.
8.
